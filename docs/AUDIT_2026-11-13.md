# Molla VPN — Repository Audit (2026-11-13)

## Scope and method

Reviewed the GitHub repository `hidooch980/Voice-Ai`, development branch
`bootstrap/molla-vpn-foundation`, backend API/auth/account/peer code, Flutter
client shell, Ansible WireGuard role, documentation and GitHub Actions history.
This is a source/configuration audit, not a penetration test or a live VPN test.

## Executive result

**Status: development foundation; not production-ready and not a usable VPN service.**

The repository contains a working backend test scaffold, a Flutter placeholder UI,
authentication primitives, persistent account/session/subscription storage, a
public-key-only WireGuard peer registry and an Ansible server template. No actual
VPN data plane, client tunnel adapter, deployed node, Cloudflare resource, billing
integration or production release has been verified.

## Repository and release governance

- Repository: `hidooch980/Voice-Ai` (public).
- Default branch: `main`; its tree currently contains only the root README.
- Development work is on `bootstrap/molla-vpn-foundation`.
- The development branch is not merged into `main`; no production release should be cut from `main`.
- Branch protection is not enabled.
- Repository license is not selected. Do not copy AGPL-3.0 reference implementation code without an explicit licensing decision and dependency review.
- No credentials or real production endpoints should be added to this public repository.

## Findings and corrections

### Backend

- FastAPI exposes only `GET /health` and read-only `GET /api/v1/protocols`.
- Protocol descriptors are correctly marked planned/disabled; no endpoint or private key is returned.
- Scrypt password hashing and HMAC-SHA256 access-token primitives exist.
- SQLite account/session/subscription persistence exists; self-registration/login HTTP routes are intentionally absent.
- Account store was hardened in this audit: database file permissions are restricted to 0600, session IDs/expiry are validated, account suspension revokes sessions, and subscription expiry is timezone-aware and enforced by an entitlement check.
- An account-scoped device registry now enforces subscription device limits and allocates IPv4 addresses within a transaction; it remains internal and is not exposed as an API.
- Account creation does not yet verify email ownership. Do not expose public self-registration until verification, rate limiting, abuse controls, recovery and audit requirements are implemented.
- There is no distributed login rate limiter, MFA, admin bootstrap workflow, signing-key rotation procedure or production secret manager integration.

### Device and peer management

- WireGuard peer registry validates canonical 32-byte public keys, subnet membership and uniqueness.
- The legacy peer registry remains an internal low-level component. A newer account-scoped DeviceRegistry now shares the account database and enforces active account/subscription state and device limits inside a SQLite transaction.
- DeviceRegistry allocates IPv4 addresses atomically, retains revoked records, and releases revoked addresses through an active-only unique index.
- Neither registry applies peer changes to a live WireGuard interface; revocation is database state only until a node-reconciliation adapter is implemented.
- No peer-configuration reconciliation or authenticated device enrollment API exists.

### Client

- Flutter is a UI shell only.
- Android/iOS/Windows/macOS runner projects and native tunnel adapters are not present.
- The connect action remains disabled, correctly avoiding a false connected state.
- No real DNS/IPv4/IPv6 leak, kill-switch, reconnect, sleep/wake, network-handoff, throughput or battery test has been performed.
- iOS/macOS builds require macOS/Xcode; Windows builds require a Windows build host.

### Infrastructure

- Ansible role is a template; it has not been executed against any server.
- The role now derives the config path from the interface name, validates basic interface/port/uplink inputs, and refuses to overwrite an unmanaged existing WireGuard config unless an explicit override is set.
- It generates a server private key on the target host and marks secret-bearing tasks `no_log`.
- Remaining deployment risks: provider firewall is unmanaged, UFW/nftables compatibility is not tested, IPv6 is not configured or leak-protected, and no client peers are provisioned.
- A WireGuard interface with no authorized peer is not a working customer VPN.
- No VPS region/provider/budget has been selected; no infrastructure was provisioned.

### Cloudflare, billing and operations

- No Cloudflare zone, DNS record, Worker, WAF rule, Tunnel or API credential was created or verified.
- No payment provider, plans/renewals/refunds, abuse workflow, support process, monitoring/alerting, backup/restore drill or incident response process is implemented.
- Cloudflare is reserved for DNS and control-plane protection; it is not treated as a generic VPN packet relay.

- Client CI passed earlier (run 43382883507), but no platform-native tunnel is included in that build.

- CI success validates only the checks actually executed. It does not validate live VPN traffic.

## Required gates before calling the product complete

1. Complete account verification, login throttling, revocable authenticated sessions, admin bootstrap, audit events and secure secret configuration.
2. Bind every device and peer to an account; enforce plan status/device limits server-side; allocate addresses transactionally.
3. Implement authenticated one-time device enrollment and short-lived configuration issuance.
4. Reconcile peer add/remove operations with the real WireGuard node and prove revocation stops traffic.
5. Implement Android's native VPN service/tunnel adapter and then independent adapters for iOS, Windows and macOS.
6. Deploy a dedicated node only after provider/region/budget approval and firewall/rollback review.
7. Pass end-to-end traffic, DNS, IPv4/IPv6 leak, kill-switch, reconnect, roaming, MTU, load and failure-recovery tests on each advertised platform.
8. Add signed/reproducible releases, SBOM/dependency review, privacy/legal review, billing, monitoring, backup/restore and support operations.
9. Merge the reviewed development branch into `main` only after all applicable CI checks pass and release gates are explicitly accepted.

## Current verdict

The code foundation is progressing and several safety controls are now present, but the
remaining blockers are substantive product work, not cosmetic checklist items. Keep
all protocol entries disabled and the connection button unavailable until real
end-to-end evidence exists.
